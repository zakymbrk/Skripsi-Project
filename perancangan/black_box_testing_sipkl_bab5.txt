1. RINGKASAN HASIL PENELUSURAN PROJECT
======================================================================

Aplikasi menggunakan CodeIgniter 3 dengan pembagian peran:
1. Admin / Hubin: level 1
2. Guru Pembimbing: level 2
3. Siswa: level 3

Alur umum implementasi:
Controller -> Model/Library -> Database -> View

Komponen utama yang ditemukan:
- application/controllers/Siswa.php
- application/controllers/Guru.php
- application/controllers/Hubin.php
- application/controllers/Auth.php
- application/models/M_presensi.php
- application/models/M_logbook.php
- application/libraries/Rule_based_validation.php
- application/views/siswa/
- application/views/guru/
- application/views/hubin/
- application/config/routes.php
- db_sipkl.sql

Tabel database yang berkaitan dengan fitur penelitian:
- tb_user
- tb_siswa
- tb_pembimbing
- tb_pengelompokan
- tb_dudi
- tb_presensi
- tb_logbook
- tb_penilaian

Rule-Based Validation terpusat pada:
application/libraries/Rule_based_validation.php

5. PENGUJIAN REKAP NILAI DAN PENALTI
======================================================================

Sumber: application/libraries/Rule_based_validation.php
Method: sync_penilaian_siswa()

Rumus yang ditemukan:
- Penalti logbook = total logbook tidak valid x 5 poin
- Penalti kehadiran = (total alpha + total terlambat) x 5 poin
- Nilai kehadiran = max(0, 100 - penalti kehadiran)
- Nilai logbook dasar = rata-rata nilai pembimbing valid, atau 100
- Nilai logbook = max(0, nilai logbook dasar - penalti logbook)
- Nilai akhir = (nilai kehadiran x 0.40) + (nilai logbook x 0.60)

Skenario tambahan:
1. Tidak ada pelanggaran: nilai penalti 0.
2. Satu alpha: penalti kehadiran 5 poin.
3. Satu keterlambatan: penalti kehadiran 5 poin.
4. Satu logbook tidak valid: penalti logbook 5 poin.
5. Kombinasi alpha, terlambat, dan logbook invalid: seluruh penalti dijumlahkan.
6. Penalti melebihi nilai dasar: nilai dibatasi minimum 0.
7. Nilai pembimbing tersedia: nilai logbook dasar menggunakan rata-rata nilai valid.
8. Nilai pembimbing tidak tersedia: nilai logbook dasar menggunakan 100.
9. Sinkronisasi ulang: tidak membuat data penilaian ganda karena menggunakan siswa_id.
10. Kolom penalti belum ada: method ensure_penilaian_penalty_columns() dijalankan.

Hasil Aktual seluruh skenario: Belum diuji
Status seluruh skenario: Belum diuji

7. TEMUAN SOURCE CODE
======================================================================

A. Implementasi sesuai rancangan
1. Pembagian role level 1, 2, dan 3 ditemukan pada constructor controller.
2. Monitoring presensi global Hubin tersedia.
3. Monitoring logbook global Hubin tersedia.
4. Guru dapat melihat data siswa bimbingan berdasarkan pembimbing_id.
5. Guru dapat memonitor presensi dan logbook siswa bimbingan.
6. Sistem memiliki endpoint lokasi siswa dan polling setiap 30 detik.
7. Validasi radius menggunakan koordinat DUDI dan perhitungan Haversine.
8. Logbook dibatasi setelah presensi masuk dan pulang.
9. Duplikasi presensi dan logbook diperkuat dengan unique key database.
10. Laporan menggabungkan presensi, logbook, dan penilaian.
11. Laporan Hubin memiliki pencarian nama dan pemilihan siswa menggunakan checkbox.

B. Implementasi sebagian
1. RBV-003 hanya memeriksa sebagian parameter dasar pada tiap alur.
2. RBV-005 terdapat konfigurasi upload format dan ukuran, tetapi tidak seluruhnya berada di library validator.
3. RBV-009 memiliki validasi file pada controller dan validator, tetapi daftar file juga menerima dokumen selain gambar.
4. RBV-011 perlu pengujian alur lengkap untuk memastikan semua jalur tanggal masa depan ditolak.
5. RBV-014 diterapkan sebagai prasyarat presensi-logbook, tetapi label rule digunakan pada beberapa kondisi yang berdekatan.
6. RBV-016 menghitung dan menyimpan nilai, tetapi pernah muncul error kolom pada database runtime.

C. Aturan yang tidak ditemukan
1. Enforcement RBV-004 sebagai kewajiban foto presensi tidak ditemukan secara konsisten pada Rule_based_validation.php.
2. WebSocket, Server-Sent Events, atau streaming lokasi kontinu tidak ditemukan.
3. Implementasi AI, Machine Learning, prediksi, dan rekomendasi otomatis tidak ditemukan pada source code yang ditelusuri.

D. Potensi ketidaksesuaian implementasi
1. Dokumentasi menyebut real-time, sedangkan implementasi aktual adalah near-real-time dengan polling 30 detik.
2. DUDI tanpa koordinat diterima sebagai tanpa_geolokasi sesuai kode, sehingga perlu konfirmasi kebijakan bisnis.
3. View presensi pulang tertentu tidak terlihat mengirim latitude dan longitude, sementara server tetap memvalidasi radius pulang. Kondisi ini berpotensi menyebabkan penolakan karena koordinat kosong.
4. Database SQL memiliki kolom total_bolos dan total_terlambat, tetapi log runtime sebelumnya menunjukkan kolom tersebut pernah belum tersedia.
5. Laporan Hubin menjalankan sinkronisasi penilaian dari view, sehingga proses tampilan memiliki efek samping pembaruan data.
6. Model global mendukung filter tanggal dan siswa melalui parameter, tetapi setiap halaman harus diperiksa agar pemanggil mengirim parameter yang benar.

E. Fitur yang perlu diuji secara manual
1. Izin browser untuk GPS.
2. GPS tidak tersedia atau timeout.
3. Koordinat tepat pada batas radius.
4. Presensi pulang melalui semua halaman yang menyediakan form.
5. Upload file dengan tipe dan ukuran batas.
6. Cetak satu siswa dan beberapa siswa.
7. Pencarian nama setelah checkbox dipilih.
8. Akses data siswa milik pembimbing lain.
9. Polling lokasi selama 30 detik dan status online 120 detik.
10. Sinkronisasi nilai setelah presensi dan logbook berubah.
11. Perbedaan struktur database runtime dengan db_sipkl.sql.

9. KESIMPULAN
======================================================================

Berdasarkan penelusuran source code, aplikasi memiliki implementasi untuk
monitoring presensi, monitoring logbook, laporan monitoring, monitoring
siswa bimbingan, lokasi siswa near-real-time, presensi berbasis radius,
riwayat presensi, dan logbook harian.

Rule-Based Validation utama berada pada Rule_based_validation.php dan dipanggil
oleh controller Siswa.php. Validasi radius menggunakan Haversine dan
membandingkan jarak dengan radius DUDI. Validasi duplikasi presensi dan
logbook juga diperkuat oleh unique key database.

Namun, seluruh hasil aktual dalam dokumen ini tetap "Belum diuji" sampai
skenario benar-benar dijalankan pada aplikasi. Beberapa kondisi perlu
mendapat perhatian khusus, yaitu enforcement foto presensi RBV-004,
perbedaan near-real-time dengan real-time, koordinat pada presensi pulang,
dan kesesuaian struktur database runtime dengan db_sipkl.sql.
